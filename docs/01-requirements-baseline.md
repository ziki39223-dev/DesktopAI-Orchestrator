# 需求基线（Requirements Baseline）

> 状态：Phase 0 定稿 · 最后更新阶段：Phase 0
> 本文是需求唯一真源。任何变更只改这里，再同步 `06-tool-contract.md` 与 `05-dev-plan.md`。

## 1. 目标

1. 一套**独立、可打包迁移**的 MCP 服务，作为“底层机械手”，不依赖任何特定编排工作台。
2. 上层编排器（主力 DSH，可无障碍切到 Cherry Studio / LangGraph）只做任务规划与结果汇总，**不启用视觉识图**，以压低充值 token 成本。
3. 后台操控本机 Trae / Qoder / WorkBuddy 三款 Electron 客户端，最大化利用三家赠送的免费额度。
4. 底层 MCP 与上层编排器**完全解耦**：本包只含 MCP 服务，不含 DSH 或任何工作台的配置。

## 2. 环境分离（硬约束）

| 角色 | 内容 | 允许做的事 | 不允许做的事 |
| --- | --- | --- | --- |
| 开发机 | 无 DSH、无 Trae / Qoder / WorkBuddy | 编码、Mock 调试、契约测试、版本管理、打包 | 依赖真机 GUI 才能跑的验证 |
| 工作机 | DSH + Trae + Qoder + WorkBuddy | 部署 MCP 服务、采集 window_rules、Real 模式联调 | 当作开发环境改架构 |

推论（必须体现在工程上）：
- 开发机上的全部测试必须能在 **Mock 模式**下通过，CI 不依赖 Windows GUI。
- Real 后端模块允许在开发机“写完但只能靠导入/静态检查验证”，真机验证项单列清单（见 `09`）。
- 任何 Real 专属依赖（`windows-capture`、`uiautomation`/`comtypes` 等）必须**延迟导入**，缺依赖时 Mock 模式仍能启动。

## 3. 自动化交互能力要求

1. **后台优先**：不强制窗口前台、不抢占屏幕焦点（参考 MaaFramework 捕获思路）。
2. **画面捕获**：DXGI / Windows Graphics Capture 窗口级捕获，窗口最小化/后台可采集（能力上限以阶段 2 实测结论回填本文附录）。
3. **控件读写**：优先 Windows UIA——读聊天输出区、向输入框写入 Prompt、触发发送。
4. **结束判定**：统一结束标记 `【Agent任务完成】`，出现即视为该轮任务结束。
5. 上述 2/3 都是“优先/后备”关系：UIA 为主路径，画面捕获作为 UIA 失效时的降级与取证手段（是否做 OCR 不在本期范围，见 §7）。

## 4. 双模式（配置开关）

| 模式 | 默认环境 | 行为 | 目的 |
| --- | --- | --- | --- |
| `mock` | 开发机 | 不触碰任何 Windows GUI 接口，返回可预期的模拟结果 | 契约验证、编排流程联调、CI |
| `real` | 工作机 | UIA + 窗口捕获，真实操作三客户端 | 生产 |

要求：模式由 `config.yaml` 单一开关控制，**同一套工具契约两模式完全一致**；切换模式不得改变工具名、入参、出参结构，只改变数据来源与错误分布。

## 5. 传输协议（双协议）

| 协议 | 定位 | 使用场景 |
| --- | --- | --- |
| SSE | 主推，网络服务模式 | 编排器经局域网/本地地址远程连接，方便随时换上层工作台 |
| stdio | 子进程模式 | DSH / Cherry Studio 原生“本地 MCP”添加方式 |

要求：两种传输**共用同一工具实现与同一后端路由**，不得为 SSE 和 stdio 各写一套业务逻辑。

## 6. 工具清单（对外暴露 4 个）

| 工具 | 入参 | 语义 |
| --- | --- | --- |
| `list_target_windows` | 无（可选过滤） | 列出识别到的 Trae / Qoder / WorkBuddy 窗口及可用状态 |
| `send_prompt` | `win_key`, `prompt` | 向指定窗口输入框写入 prompt，自动追加结束标记约定，并发送 |
| `fetch_output` | `win_key` | 读取聊天区最新输出，检测结束标记，返回完整结果与完成状态 |
| `reload_window_rules` | 无（可选路径） | 重载 `window_rules.json`，适配客户端版本更新 |

注：`reload_window_rules` 与需求原文一致；入参细节、返回结构、错误码在 `06` 中冻结。

## 7. 明确不做（本期范围外）

1. 抓包、逆向 Electron 私有接口、注入脚本进客户端渲染进程——**只走 UIA / 系统原生窗口 API**。
2. 视觉识图 / 多模态截图理解（成本控制要求，且上层编排不做识图）。
3. OCR 兜底、坐标点击兜底（阶段 2 若发现 UIA 完全不可用，作为**变更请求**单独评估，不进本期）。
4. DSH 的 Agent 角色 Prompt、流水线 DAG、人工审批节点配置。
5. 毕设项目目录、`COLLABORATION.md`、产物 md 文件——由编排侧/项目侧单独管理。
6. 账号池、多实例并发抢额度、自动登录、验证码处理。

## 8. 已知风险与限制

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 三款客户端是 Electron 壳，UIA 控件 ID 随版本变动 | Real 模式定位随时失效 | 控件选择器全部外置到 `window_rules.json`，支持热重载；规则带版本号与采集日期 |
| 窗口最小化后捕获可能返回黑帧 | 取证/降级能力受限 | 阶段 2 实测记录各客户端在最小化/后台/遮挡三态下的捕获结果，回填附录 |
| 后台写入可能被客户端判定为“非用户输入”而丢弃 | 发送失败 | UIA SetValue + 焦点/发送键组合的多策略降级，失败显式报错给编排器 |
| 免费额度触发限流/排队 | 长等待 | `fetch_output` 带超时与轮询策略，把“未完成”作为正常状态返回而非异常 |
| MCP 传输协议版本差异（SSE 端点约定） | 不同工作台连不上 | 两种传输都提供自测脚本 + Inspector 用例（`10`） |

## 9. 验收口径（Definition of Done）

阶段级 DoD 见 `05-dev-plan.md`。项目级总验收：

1. 在工作机上，仅凭“拷贝文件夹 + 改 `config.yaml` + 填 `window_rules.json`”即可跑通 Real 模式，不需要开发机参与。
2. Mock 模式下，四个工具通过 MCP Inspector 全部联通，且契约与 Real 完全一致。
3. SSE 与 stdio 两种传输均能被至少一种工作台接入（SSE 用 DSH，stdio 用 Cherry Studio 或 Inspector）。
4. 上层编排器不做任何识图，仅靠工具返回值即可完成“下发 → 轮询 → 结束标记 → 取回结果”闭环。
5. 任一失败场景（窗口不在、控件错位、超时）都能返回**结构化错误**而不是抛裸异常，编排器可据此决策。
